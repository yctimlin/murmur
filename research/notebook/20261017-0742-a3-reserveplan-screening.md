# Long greenfield screening task: reserveplan

- Question: Can we freeze a substantial Python-only greenfield task covering several interacting modules, without tying it to a protocol hypothesis?
- Method: Wrote a public product specification for deterministic dependency/resource scheduling, a clean specification-only git input, and 74 behavioral grading cases. Input generation has fixed git identities/dates and no network dependency. Scoring copies the delivered tree, runs independently located hidden tests, and prints final JSON.
- Prediction: Expected solo implementation time is 65 minutes. Intended solo hidden-score range is 60–85%, especially sensitive to capacity-calendar interaction, schema paths, and CLI failure preservation. These are design judgments, **not calibrated results**; phase A prohibits new lab runs, and no implementation-agent trial was run.
- Raw/derived paths: `research/tasks/reserveplan/{TASK.json,brief.md,SPEC.md,make_input.sh,score.sh,hidden/cases.py,hidden/score.py}`. Baseline generated at `research/tasks/reserveplan/input` (ignored). Commands: `make_input.sh`; `score.sh input`; a direct import of `hidden/cases.py` comparing each bounded concrete plan expectation with `oracle(value)`.
- Result: Untouched input scores **0/74, rate 0.0** in 0.19 seconds. Independent minute-grid oracle matches all **25** bounded fixed-plan expectations; the 26th is the separately checked billion-minute boundary case (start=999999990, end=999999993). All four fixed-seed oracle workloads are feasible. Python compilation passes. The generated input has an initial commit and no implementation.
- Decision: Mark as greenfield multi-module and long. Request a2's independent review before freezing. Do not claim the intended score/time range has been established empirically. Scoring does not grade installability because Python alone does not guarantee an offline build backend.
